# cindro-acp — Agent Client Protocol bridge for Cindro

Drive **Cindro** from **Zed** (or any [Agent Client Protocol](https://agentclientprotocol.com)
client — JetBrains, etc.) as a native agent. The editor spawns `cindro-acp`, talks
**newline-delimited JSON-RPC 2.0 over stdio**, and this bridge translates every ACP
call to/from the `jarvisd` **Contract A** control WebSocket
(`ws://127.0.0.1:8795/control/ws`). You get real Cindro sessions, streamed turns,
tool-call visibility, and permission prompts — inside your editor.

```
Zed  ──ACP JSON-RPC (stdio)──▶  cindro-acp  ──Contract A (loopback WS)──▶  jarvisd
        session/new/prompt/…         │  session.create/send/subscribe/…
        ◀── session/update ──────────┘  ◀── session.event {ev:{kind,…}} ──
```

## What it maps

| ACP (editor ⇄ bridge) | Contract A (bridge ⇄ jarvisd) |
| --- | --- |
| `initialize` | `ping` (reachability) → advertises `promptCapabilities.text`, `loadSession` |
| `session/new` | `session.create {profile:"coworker", title:"ACP: <client>"}` → **`session.subscribe` immediately** (scoping guard) |
| `session/load` | `session.subscribe` + replays `session.history` as `session/update`s |
| `session/prompt` | `session.send {text}`, then streams `session.event`s until `final`/`error` |
| `session/update` ⟵ `agent_message_chunk` | `message` (role≠user) |
| `session/update` ⟵ `agent_thought_chunk` | `thinking` |
| `session/update` ⟵ `tool_call` / `tool_call_update` | `tool_call` / `tool_result` (status + `rawInput`/`rawOutput`) |
| `session/request_permission` | `approval {approval_id,summary,risk}` → `approval.respond {decision}` |
| `session/cancel` | `session.cancel` |
| `stopReason: end_turn / refusal / cancelled` | `final` / `error` / cancel |

Permission mapping: `allow_once → allow`, `allow_always → always`,
`reject_once`/`reject_always`/cancelled → `deny`.

Events are **strictly session-scoped**: the bridge subscribes each session on the
shared control socket and fans events into per-session queues, so another chat's
(or a subagent's) events never leak into your editor.

## Install

`cindro-acp` depends only on `websockets`. Install it into an isolated environment:

```bash
# with pipx (recommended — gives you a stable `cindro-acp` on PATH)
pipx install /path/to/computer_use/acp-bridge

# or with uv
uv tool install /path/to/computer_use/acp-bridge

# or a plain venv
python3 -m venv ~/.local/share/cindro-acp-venv
~/.local/share/cindro-acp-venv/bin/pip install /path/to/computer_use/acp-bridge
# -> binary at ~/.local/share/cindro-acp-venv/bin/cindro-acp
```

## Wire it into Zed

Add an entry under `agent_servers` in Zed's `settings.json`
(`~/.config/zed/settings.json`), then pick **Cindro** in the agent panel:

```json
{
  "agent_servers": {
    "Cindro": {
      "command": "cindro-acp",
      "args": [],
      "env": {}
    }
  }
}
```

If `cindro-acp` isn't on Zed's PATH, use the absolute path from your install
(e.g. `"command": "/home/you/.local/bin/cindro-acp"` for pipx, or the venv's
`bin/cindro-acp`). Other ACP editors take the same `command` + `args` + `env`.

## Auth notes

There is **no ACP-level auth** (the bridge advertises `authMethods: []`). Contract A
is a loopback-only, token-gated socket, and the bridge reads that token itself:

- **Token:** `~/.config/jarvis/control_token` (0600, auto-generated by `jarvisd`),
  overridable with the `JARVIS_CONTROL_TOKEN` env var.
- **Endpoint:** `ws://127.0.0.1:8795/control/ws`, overridable with `JARVIS_CONTROL_WS`.

`jarvisd` must be running locally. If it isn't, `initialize` still succeeds (so the
agent appears in Zed) and the bridge reconnects with backoff; `session/new` fails
with a clear error until the daemon is up.

## Environment variables

| Var | Default | Meaning |
| --- | --- | --- |
| `JARVIS_CONTROL_WS` | `ws://127.0.0.1:8795/control/ws` | Contract A control WS base URL |
| `JARVIS_CONTROL_TOKEN` | *(reads `~/.config/jarvis/control_token`)* | Contract A bearer token |
| `JARVIS_ACP_FRAMING` | `ndjson` | stdio framing; set to `content-length` for LSP-style `Content-Length` framing |
| `JARVIS_ACP_LOG` | `INFO` | log level (diagnostics go to **stderr**; stdout is the protocol channel) |

## Develop / test

```bash
# engine venv already has websockets + pytest:
cd acp-bridge && env -u PYTHONPATH \
  /path/to/computer_use/computer-use/.venv/bin/python -m pytest tests -q

# or a local dev venv:
python3 -m venv .venv && .venv/bin/pip install -e . pytest
.venv/bin/python -m pytest tests -q
```

Tests run against a **fake Contract A daemon** (an asyncio `websockets` server that
emits canned `NormalizedBrainEvent` sequences) — no real `jarvisd` needed.
